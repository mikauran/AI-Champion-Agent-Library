# MCP test platform

A black-box scorer for MCP servers. It talks to a server over stdio or Streamable HTTP, points the server at an offline mock upstream with seeded synthetic data (and optional fault injection), runs 12 cases and rolls the results up into one report. Servers generated by the Phase 14 generator and submitted servers are scored the same way. Everything is synthetic: no credentials, no real data and no real API are involved.

What was ported from the study harness, what was re-implemented and what is a known gap is recorded case by case in `docs/mcp-test-port-fidelity.md` (machine-readable twin: `src/lib/mcptest/core/fidelity.ts`). Read that first if you need to compare scores with the study.

## Status and honest gaps

- **Fake variants are scorer fixtures.** The in-process fake servers (`fake:good`, `fake:mirror`, ...) exist to prove the scorer discriminates good from flawed behaviour. A fake result is never evidence about a real server.
- **No real FastMCP server has been run by this platform.** Generated Python is never executed in CI; those cells report `PENDING_HUMAN`. See "Pending human" below.
- **The headline score formula is an assumption** (unweighted mean of Tier 2 and Tier 3 case pass-rates) pending confirmation by the study author.
- **D3 (documentation quality) is advisory and D5 is not scored.**
- Legacy HTTP+SSE is not implemented (reported as unsupported). The real partner profile document is not available, so the profile case scores an invented Acme profile only. The generator emits stdio only, so HTTP cases give `NA_TRANSPORT` for generator subjects, and it cannot produce composite tools.
- The runner image has never been built; container runs are pending human.

## Flag and runtime variable

| Variable | Default | Effect |
|---|---|---|
| `MCP_TESTER` | off (`1`, `true`, `on`, `yes` enable) | Enables the `/mcp-test` page, the `/api/mcp-test/*` routes and a Customize menu entry. Independent of `MCP_GENERATOR`. Off: the routes return 404 and the menu is unchanged. |
| `MCP_TESTER_RUNTIME` | unset | `container` makes web runs execute inside the sandboxed runner image through the Phase 8 container runtime. Any other value or unset: runs score in process against fake variants and generator samples. It is an operator opt-in and is set in no committed file. |

The CLI ignores `MCP_TESTER` (it is an author tool, like `generate-mcp`).

## How to run

### CLI

```
npm run mcp-test -- --list
npm run mcp-test -- --subject fake:good
npm run mcp-test -- --subject generator:openapi --case T2-CATALOG-API --reruns 3 --format markdown --out /tmp/report.json
npm run mcp-test -- --subject cmd:"/tmp/mcp-venv/bin/python /tmp/acme-server/<server-dir>/server.py" --env-base-url <BASE_URL_VAR> --env-api-key <API_KEY_VAR> --case T2-CATALOG-API --reruns 3 --allow-local-exec --out /tmp/report.json
```

Flags: `--subject`, `--case ID` (repeatable), `--reruns 1-3`, `--format text|markdown|json`, `--out FILE`, `--allow-local-exec`, `--env-base-url NAME`, `--env-api-key NAME`, `--list`. A `cmd:` subject is a real process and is only spawned with `--allow-local-exec` (no shell, argv split, allowlisted environment, fresh temporary HOME). The exit code is 0 on a PASS verdict (or `--list`), 1 for any other verdict, 2 for usage errors.

### UI

With `MCP_TESTER=1`, open `/mcp-test` (linked from the Customize menu). Choose a subject (fake variants and generator samples), optionally narrow the cases and reruns, start the run, watch progress and download `report.json`. The page stores nothing and polls.

### API (flag-gated)

- `POST /api/mcp-test/runs` with `{ "subject": "fake:good", "cases": [...], "reruns": 1 }` returns 202 and `{ id, status: "queued" }`. Body is capped at 4096 bytes; only known fake variants and generator samples are accepted (no uploaded code, no `cmd:` subjects).
- `GET /api/mcp-test/runs/{id}` returns status, progress and recent events.
- `GET /api/mcp-test/runs/{id}/report` returns the report JSON when done.

Starts are limited to 10 per client per 10 minutes. Runs are kept for 30 minutes (at most 50, finished runs evicted first). The routes derive a session key and rely on the application's global hook for authentication (see pending human item 8).

## The 12 cases

Tier 1 is the gate; Tier 2 and Tier 3 carry the score; Tier 4 raises risk flags.

| Case | Tier | What it checks |
|---|---|---|
| T1-STD-CATALOG | 1 | Synthetic catalog gate: the server starts, negotiates, lists tools and answers the basic behaviour checks. A failed gate disqualifies the server. |
| T2-CATALOG-API | 2 | The 10 behaviour checks below against the mock REST upstream, plus a behaviour pack. |
| T2-CATALOG-DUMP | 2 | Same idea over a dump-backed server. Needs a real runtime and a data path; fake subjects report `PENDING_HUMAN`. |
| T2-CATALOG-HTTP | 2 | Client side of the Streamable HTTP transport. Generator subjects get `NA_TRANSPORT`. |
| T3-RT-DOCS | 3 | Grounding: every upstream route the server calls must be documented in the invented manual; an undocumented route scores D3 = 0. |
| T3-PROFILE-CONTRACT | 3 | Required tools, naming and descriptions against an invented Acme profile. |
| T3-COMPOSITE | 3 | A composite tool assembles data from two upstream resources. |
| T3-LARGE-RESP | 3 | Large seeded set: response size is capped and truncation is signalled (tokens approximated as bytes/4). |
| T4-FAULT-UPSTREAM | 4 | Seeded faults: retries (2 to 6 attempts), timeout handling, malformed upstream bodies (fabricated answers raise a blocker). |
| T4-PARTIAL-SPEC | 4 | Generator side, in process: a partial spec must yield reported gaps; reruns must be byte-identical. |
| T4-SEC-SECRETS | 4 | A canary key must never be echoed, no write tools on a read-only source, injection text is not obeyed. |
| T4-I18N-CODES | 4 | Codes with a check digit are validated before any upstream call. |

The 10 generic behaviour checks (ids in the fidelity map): `lookup_by_id`, `lookup_by_alt_key`, `partition_filter`, `derived_filter`, `projection`, `pagesize_clamp`, `pagination_ceiling`, `bad_input`, `empty_vs_error`, `auth_fail`. Pass conditions are deliberately tighter than the study harness (strict not-found signal, no vacuous derived-filter pass, ambiguous tool binding is a scorer ERROR); each tightening is listed in the fidelity map and in the decision log.

## Scoring rules

- **Gate.** Tier 1 cases that ran must pass. A failed gate gives no headline score and verdict `DISQUALIFIED` (Tier 2 results are still shown).
- **Case result.** Pass rate over scored checks (NA excluded, ERROR counted as not passed). `pass_thresholds` of a case are enforced when at least one is scorable; unscorable ones are listed, not assumed met. A failed D1 (the server starts and answers) can never be thresholded away.
- **Dimensions.** D1 starts and answers, D2 functional, D3 documentation (advisory), D4 robustness, D5 not scored, D6 cost and time (no LLM, zero tokens; reproducibility for generators).
- **Headline score.** Unweighted mean, one decimal, of the Tier 2 and Tier 3 case pass-rates over cases that ran. `null` when the gate fails. Assumption pending confirmation.
- **Flags.** Blockers: `LEAK`, `SECRET_ECHO`, `WRITE_TOOL`, `CONFIDENT_WRONG`. Warnings: `NO_RETRY`, `SILENT_GUESS`, `UNVALIDATED_CODE`, `STDOUT_NOISE`.
- **Verdict precedence.** A blocker flag gives `BLOCKED`; else a failed gate `DISQUALIFIED`; else nothing ran `INCOMPLETE`; else all applicable Tier 2/3 cases ran and passed `PASS`; else `FAIL`. A scoring case that is `PENDING_HUMAN` stops the verdict at `FAIL` (a good fake over all 12 cases reports `FAIL` at coverage 6/7 because the real-runtime dump case is pending human). This rule is recorded as a decision with its alternative.
- **Reruns.** 1 to 3 (default 1 in the API and CI). Majority vote per check; ties go to FAIL.
- **Cell states.** `PASS`, `FAIL`, `NA_MODALITY`, `SKIPPED_FIXTURE`, `UNAVAILABLE`, `INSTALL_FAILED`, `GEN_FAILED`, `ERROR` (scorer problem, not a server verdict), `NA_TRANSPORT`, `PENDING_HUMAN`. The legend ships inside every report.

## Report schema

`mcptest-report/1` (zod schema `ReportSchema` in `src/lib/mcptest/core/report.ts`): subject, runtime label, per-case cells with checks, dimensions and flags, tier rollup, gate, headline score, verdict, coverage, a pending-human list with exact commands, and the state legend. Reports are capped at 1,000,000 bytes, reasons at 200 characters, and secrets and the per-run canary are redacted from every string. `renderSummary` and `renderMatrix` produce the human-readable text and markdown; `toLegacyCsvRow` gives an optional legacy CSV row.

## Adding a case

A case is a directory under `src/lib/mcptest/suite/<CASE-ID>/` using the source-compatible formats:

- `case.yaml` (id, tier, modality, thresholds), `golden.jsonl` (one check per line; blank lines and `#` lines are skipped; additive fields `inject`, `repeat`, `check_kind`), `rubric.yaml` (advisory items).
- Platform keys use an `x-` prefix (`x-upstream`, `x-env`, `x-binding`, `x-identity`, `x-applies-to`, `x-strict`, `x-ceiling`, `x-requires`) and are ignored by the source format.
- Fixtures live in the case directory; only synthetic Acme-style content is allowed. A golden-isolation test fails if an expected string appears in a fixture shown to a generator.
- Register the id in `src/lib/mcptest/core/fidelity.ts` (`CASE_IDS`, the case table) and `KNOWN_CASE_IDS` in `src/lib/mcptest/driverRequest.ts`, and add a row to `docs/mcp-test-port-fidelity.md`. Tests pin these lists against each other.

## Adding a subject

Implement the `Subject` interface (`src/lib/mcptest/core/types.ts`): `prepare` must never throw and returns a status, a launch descriptor (stdio command or loopback HTTP URL), optional tool binding and the environment variable names to fill with the mock URL and key. Register it in `src/lib/mcptest/core/subjects.ts`. New fake behaviours go in `src/lib/mcptest/fake/variants.ts`; every description must start with `Scorer fixture:`.

## Safety rules

- The runner never touches a real API or key. The mock binds 127.0.0.1 on an ephemeral port and answers a non-loopback Host header with 421; the HTTP transport accepts only loopback hosts.
- Subject processes get an allowlisted environment (never `process.env`), a fresh temporary HOME and a per-run random canary key that is redacted from reports. Spawning requires an explicit `allowLocalExec`.
- Container runs use a dedicated image, an internal network without egress, no LLM proxy and no tools; `MCPTEST_ALLOW_OPEN_EGRESS` is refused.
- Generated Python is never executed in CI. The core, mock and fake modules import nothing from `$lib` or Svelte, and only `core/transports/stdio.ts` imports `child_process`. An invariant test (`src/lib/mcptest/criteria.test.ts`) enforces these rules, the absence of secrets and non-loopback URLs, and that the flag is off by default.

## Limits

Body 4096 bytes; request to the driver 64 KiB; package up to 200 files and 2,000,000 bytes; driver tree up to 800 files and 6,000,000 bytes; report 1,000,000 bytes; 200 events of 300 characters per run; 10 starts per client per 10 minutes; default container job timeout from `MCPTEST_JOB_TIMEOUT_MS`.
