## Summary

The source study contains two different things that must not be conflated. (a) `harness/harness.py` + `expected.py`: a one-API, live-key grader of a single server with 10 checks; it is a rubric and a set of validator functions, not portable as-is. (b) `wp5-bench/`: a modality-aware runner that, per (case x arm x rerun), has a generator "arm" produce a server from a fixture, launches it over stdio, and runs a `golden.jsonl` against a mock upstream; plus a report matrix, a leak guard and an arm registry. Only one of the 12 designed cases (`T2-STK-API`, 9 golden checks, rubric, offline Python mock) exists. The platform's unit of scoring changes subtly: it scores a SERVER (a "subject"), and optionally first produces that server with the Phase 14 generator. So D1's "generates" half and D6 apply only to generator subjects; for submitted or fake servers they are reduced or N/A, and the report must say so.

Everything portable is logic, not code: validators (field-name-agnostic dict walking, regex word lists, the leak detector, the 12-field projection cap), the golden/binding formats, the run-state vocabulary (PASS, FAIL, NA_MODALITY, SKIPPED_FIXTURE, UNAVAILABLE, INSTALL_FAILED, GEN_FAILED, ERROR), and the report matrix. These are re-implemented in TypeScript (about 1,500 lines, no new dependencies) because the runner is welded to the Python `fastmcp` Client and Python mock servers. Several source quirks should be fixed deliberately, not ported: lenient `clean_not_found`, optimistic majority tie-break in `report.py`, unread `pass_thresholds`, first-regex-match tool binding, whole-environment inheritance into the server subprocess, and a leak-guard length mismatch (all in Pitfalls).

For real runs, the Phase 8 `ContainerRuntime` contract (`putFiles` / `exec` / `getFiles` / `remove`) cannot drive a stdio MCP server directly because `exec` has no stdin. The recommended fit that needs NO contract change is an in-container driver: stage the case bundle, the subject package and a bundled driver, run the driver with `exec`, collect `report.json` with `getFiles`. The mock upstream lives inside the same container on loopback, so the container can use an internal (no-egress) network. This needs a new image (Node plus Python plus pinned FastMCP) and a second `RunnerConfig`; building and running it is pending human. CI uses an in-process fake MCP server written in TypeScript (framing over Node streams, plus one real-subprocess smoke test) with intentionally flawed variants that prove the scorer discriminates.

**Primary recommendation:** Build `src/lib/mcptest/` as a pure-TypeScript core (own minimal JSON-RPC/MCP client, no `@modelcontextprotocol/sdk`; Node `http` mock upstream with seeded fault injection; source-compatible `case.yaml`/`golden.jsonl`/`rubric.yaml`; fake server with flawed variants), a thin server layer reusing Phase 8 job/route patterns behind `MCP_TESTER`, and list every real-FastMCP/container run as pending human.

## Port-Fidelity Map

Legend for "Port decision": **Ported** = logic carried over 1:1 (rewritten in TS because the host language differs; semantics identical and test-pinned); **Wrapped** = original artefact is invoked or consumed unchanged; **Re-implemented** = same purpose, deliberately different mechanics; **Not ported** = left out with reason. Nothing in the source is Wrapped literally (no Python is run by the platform); where the roadmap says "reused or wrapped where possible", the reuse is of formats (case.yaml/golden.jsonl/rubric.yaml/registry.yaml shapes) and of validator logic.

## Scoring Semantics to Preserve

1. **Tier 1 gate.** A subject failing any Tier 1 case is DISQUALIFIED for that source: report `gate: "fail"`, `score: null`, and still show Tier 2-4 results informationally. Never average a gate failure away. Gate pass thresholds are those of `case.yaml` (T1: D1 pass, D2 >= 95%, D3 = 3).
2. **Tier 2 + Tier 3 carry the score.** The source gives no formula. Recommended and logged as an assumption: per-case score = passed / scored checks (NA excluded, exactly like the harness's 9-of-9 convention); headline = unweighted mean over Tier 2+3 cases that ran, reported together with `casesRun/casesApplicable` so a subject cannot look good by skipping cases. Case-level `pass_thresholds` (D2 pct, D3 score, `pagination_correct`, `result_cap_present`) decide case PASS/FAIL, which the source runner never enforced.
3. **Tier 4 = risk flags, not points.** Flags have severity `blocker` or `warning`. Blockers: raw error leak, secret/canary echo, spurious write tool from a read-only source, confident wrong answer on malformed upstream data. Warnings: no retry/backoff on 429/5xx, silent guessing (variance across reruns), unvalidated domain codes. Verdict precedence: any blocker means `BLOCKED` regardless of score ("a leak or a spurious write tool is a blocker regardless of score").
4. **Dimensions (D1-D6).** Per the suite doc: D1 binary, D2 %, D3 0-3, D4 %, D5 0-3, D6 measured. Reality in the study (HIGH confidence, `results.csv` has only the 10 harness checks): D3 and D5 were never scored; the 10 harness checks map to dimensions only by Phase 14's own table (D2: checks 1-5; D4: checks 6-10; D1 implicit). Platform behaviour:
   - D1: pass if the process launches, `initialize` succeeds, `tools/list` returns within timeout (and the health GET answers for HTTP). "Installs" cannot be checked in CI (container build = pending human).
   - D2: golden `call` checks tagged D2 plus harness checks 1-5, as a percentage.
   - D3: rubric items automatable from `tools/list` and outputs (tool names vs contract, param names, multilingual fields present, pagination params named) produce a 0-3 score labelled `advisory`; items needing source reading are `manual`. For a case with no automatable items D3 is `not_scored`.
   - D4: harness checks 6-10 plus golden checks tagged D4 plus T4 fault checks, as a percentage; NA excluded.
   - D5: never part of the headline. Only when the generated package source is available (generator subjects) run static advisory checks (type hints present, env-var config, no URL/secret literal, test file present); otherwise `not_scored`. Same status as the source: defined, never scored.
   - D6: only measurable parts: generator wall-clock, per-case wall-clock, reproducibility across reruns (equivalence of check outcomes; byte-identical output hash for the deterministic generator). Tokens/cost = 0 with `llm:false`; human interventions = not applicable. Be plain about this in the report.
5. **Reruns.** Source: at least 3 reruns, report median and spread; matrix uses majority vote. Port: default 3 for real subjects; reruns of deterministic subjects are cheap. Majority tie-break = FAIL (pessimistic), a documented deviation.
6. **Run states are never conflated.** Cell states: PASS, FAIL, NA_MODALITY, SKIPPED_FIXTURE, UNAVAILABLE, INSTALL_FAILED, GEN_FAILED, ERROR (source) plus additive `NA_TRANSPORT` and `PENDING_HUMAN` (real runtime required, not executed). Check states: PASS, FAIL, NA (+ `ERROR` for unbound or ambiguous binding). Report them separately; do not average N/A into a score.
7. **Leak detector (`looks_like_leaked_error`), exact.** Applied to the lowercase-insensitive text blob (all text content plus structured content): leak if any of these substrings occurs (case-sensitive): `Traceback (most recent call last)`, `httpx.`, `all shards failed`, `requests.exceptions`, `ConnectionError`, `JSONDecodeError`; OR if at least 3 of the 4 words `timestamp`, `status`, `error`, `path` occur anywhere in the lowercased blob (the "raw upstream envelope" rule, upstream error shape `{timestamp, status, error, path}`). Port exactly, keep the six strings as the CORE set, and add an extensible per-runtime set (Node stack markers, `ECONNREFUSED`, `undici`, `at Object.<anonymous>`). Our own error shape must use keys like `ok`, `kind`, `message`, `hint` (never 3 of the 4 words); record WHICH rule fired in the reason so false positives are diagnosable.
8. **Order of evaluation in bad_input** (explicit not-found before product detection) and **auth words** (stricter harness regex; the runner's looser `invalid` alternative is not ported) are preserved.
9. **Generated-server guarantee set.** Phase 14's behaviour checklist 1-9 (RESEARCH-SYNTHESIS 3.2) is the contract the case pack asserts; its pytest tests are seed cases, not a substitute (they run against a stub, not through MCP).

## MCP protocol: the minimal client

Source: official spec, transports page (`modelcontextprotocol.io/specification/2025-11-25/basic/transports`, fetched 2026-10-12). HIGH for stdio framing and Streamable HTTP rules; the exact tools/list and tools/call result shapes are from the spec as recalled and must be confirmed against a real server (MEDIUM).

**stdio framing:** client launches the server as a subprocess; messages are single-line UTF-8 JSON-RPC objects delimited by `\n`, with no embedded newlines; the server may log to stderr (client must not treat stderr as an error); the server must not write non-MCP content to stdout; shutdown = close stdin, then SIGTERM, then SIGKILL. (Not Content-Length framing.)

**Lifecycle the scorer implements:**
1. Send `initialize` request: `{ protocolVersion: "2025-11-25", capabilities: {}, clientInfo: { name: "aic-mcp-tester", version } }`. Accept any server-chosen version in a known set (`2025-11-25`, `2025-06-18`, `2025-03-26`, `2024-11-05`) and record it; an unknown version is a D1 finding, not a crash.
2. Send notification `notifications/initialized`.
3. `tools/list`, following `nextCursor` until absent (page cap to avoid loops). Record names, descriptions, `inputSchema`, `annotations`.
4. `tools/call` with `{ name, arguments }`. Result: `content[]` (text items), optional `structuredContent`, `isError`. A JSON-RPC `error` response (for example unknown tool or invalid params) is a protocol-level outcome DISTINCT from `isError: true` (a tool-level error); validators must treat both as "clean error signal" only if the text has no leak, as the harness does for exceptions at transport level.
5. Handle server-to-client messages: answer `ping`, reply `-32601` to any other request (sampling, roots), ignore notifications (`notifications/message`, `tools/list_changed`).
6. Per-request timeouts, id correlation, size cap per line (reject lines above a limit, record `oversize_message`), capture stderr (cap 64 KiB) for secret scanning only.

**HTTP (declared transports):** Streamable HTTP: POST each message to the MCP endpoint with `Accept: application/json, text/event-stream`; response is either JSON or an SSE stream containing the response; carry `MCP-Session-Id` if issued and `MCP-Protocol-Version` on later requests; notifications get 202; DELETE to end the session. The old HTTP+SSE transport (2024-11-05) is deprecated: designed-only gap, listed in the report as unsupported rather than silently skipped. The source's "SSE transport with health check" (T2-STK-HTTP) should be read as Streamable HTTP plus a non-MCP `GET <health path>` configured in `case.yaml` (open question 3).

### Pattern 1: Subject interface (port of the adapter contract)
Never throws; every failure is a status. `prepare()` yields a `launch` descriptor, never a live process, so the same cell logic runs in CI, a container driver or a human CLI.
```ts

  | { kind: 'stdio'; command: string; args: string[]; cwd: string }   // executed ONLY by a runtime that is allowed to
  | { kind: 'inproc'; serve: (r: Readable, w: Writable, env: Record<string,string>) => Promise<void> }
```

### Pattern 2: Cell orchestration (port of `run_case`)
Resolution order is verbatim from `runner.py`: `unavailable` -> `install_failed` -> modality resolution (`NA_MODALITY` if the subject's modality is not in `provides_modalities`; `SKIPPED_FIXTURE` if planned but the fixture dir is empty) -> prepare (`GEN_FAILED`) -> run checks. Add before check execution: `PENDING_HUMAN` when `launch.kind==='stdio'` and the active runtime is not allowed to execute it; `NA_TRANSPORT` when the case needs HTTP and the subject only offers stdio.

### Pattern 3: Binding (port of `binding.json`, and answer to synthesis Q7)
Per-case golden entries reference tools by `tool` (exact) or `tool_hint` (regex). Per-subject override `binding.json` maps check id -> `{tool, args}` exactly like the source. Recommendation for Q7: the CASE owns the generic checks and hints; the SUBJECT may ship a `binding.json` (generated servers: derive it in-process from the Phase 14 plan, which knows each tool's kind via `toolKind`, so no Phase 14 change is required for in-process use; a small additive `bindings` field in `report.json` would let downloaded packages be scored later). Bound-by (`explicit` / `hint`) is recorded; an ambiguous hint is `ERROR`.

### Pattern 4: Mock upstream with fault injection
One Node `http` server per cell, bound to `127.0.0.1:0` (ephemeral, no collision unlike the source's random 19000-19999), torn down per cell; state reset per rerun. Route behaviour is declared in `case.yaml` under `x-upstream` (dataset name, routes, auth mode, max page size, ceiling) plus code-registered handlers for the few non-declarative needs (composite, docs route-log). Fault controller API (called by the runner between golden steps, or declared on a golden line as `inject`):
- status: any code, optional `Retry-After`, optional legacy envelope body `{timestamp,status,error,path}` (for the leak test)
- latency: fixed or seeded jitter; timeout (never answer until the client aborts)
- malformed: truncated JSON, wrong content-type, HTML body, empty body, huge body (N MB), slow-drip, connection reset
- flapping: fail first N calls of a route, then succeed (retry proof)
- auth: required header or query key, accepted-value check; 401/403 envelope
- ceiling: `page*size > N` returns 500 "all shards failed"-style text (synthetic)
- request log: method, raw path, query, header NAMES only (never values), count per route, timestamp offsets (backoff proof); exposed to validators and to the Tier 4 checks
The mock must also reject unknown query parameters with 400 so a server cannot satisfy the derived-filter check through a parameter the "real API" lacks.
Determinism: seeded PRNG (mulberry32) for datasets and jitter; same seed gives the same bytes.

### Pattern 6: Real runs via an in-container driver (Phase 8 fit, pending human)
Phase 8 contract (read from `runtime.ts`): `ping`, `ensureNetwork`, `createAndStart(spec)`, `putFiles`, `exec(cmd, workingDir, onStdout, onStderr)`, `getFiles(dir, {maxBytes,maxFiles})`, `remove`, `listManaged`. `ContainerSpec` carries only name/labels/env; image, limits and network come from `RunnerConfig`; the dockerode runtime drops all capabilities, uses a read-only root filesystem and `NetworkMode: cfg.network` (internal network). `exec` has NO stdin, so a stdio MCP client cannot sit on the host and talk to a process in the container through this contract.
Recommended flow (no Phase 8 change):
1. New image `localhost/mcp-test-runner:latest` (Containerfile.mcp-test-runner): Node >= 22.19 + Python 3 + `tsx` pinned + FastMCP pinned (human decides the pin) + the dependencies the generated `requirements.txt` needs, installed at BUILD time so runtime needs no network.
2. A second `RunnerConfig`/`createDockerodeRuntime(cfg, instanceId)` instance with that image and an internal network (never the Pi proxy network, no LLM token env).
3. `createAndStart` (labels `aic.tryitout`-style owner label so the Phase 8 orphan sweep/leases semantics apply or a distinct `aic.mcptest` label with its own sweep) -> `putFiles` (case bundle, subject package, bundled `driver.ts`) -> `exec ["tsx","/work/driver.ts"]` (driver starts the mock on loopback, spawns the Python server as a child, runs the suite, writes `/work/out/report.json`) -> `getFiles('/work/out', limits)` -> `remove` in `finally`.
4. Container never receives a real URL or key; the canary key is generated per run.
A second option (human decides): extend `ContainerRuntime` with an `attach`/stdin-capable exec. More general, but touches Phase 8 and both runtimes; not recommended for this phase.

How a Phase 14 generated Python FastMCP server is run: only inside that container (or a human-made venv via the CLI `--allow-local-exec`). CI never executes generated Python (14-VERIFICATION: "no generated Python was ever executed, only py_compiled"); CI scores the fake and runs the generator-side checks in-process. Real runs of generated servers: PENDING HUMAN.

### Anti-Patterns to Avoid
- Inheriting `process.env` into the server subprocess (source does `os.environ.copy()`): use an allowlist (`PATH`, `LANG`, a temp `HOME`) plus only case-declared vars.
- Letting a hint pick the first regex match.
- Scoring through a mock that exposes the discriminator capability natively.
- Putting `core/` behind SvelteKit aliases (breaks the container driver).
- Calling a fake-variant result "the generator's score".

## Common Pitfalls

### Pitfall 1: The scorer leaks real values or environment (SC-3)
**What goes wrong:** copying `expected.py` literals or the captured real fixture; inheriting the developer's env (which holds keys) into the subprocess.
**How to avoid:** all fixtures synthetic Acme data generated from a seed; env allowlist; canary key only; a criteria test (Phase 14 `criteria.test.ts` precedent) scanning `src/lib/mcptest` and docs for reference-repo names, study-specific tokens, secret-shaped strings and any non-loopback URL.
**Warning signs:** any 7-digit domain id, real brand or API host appearing in a diff.

### Pitfall 2: Executing untrusted server code on the host
**What goes wrong:** "test any submitted MCP server" equals arbitrary code execution. The API/UI must not accept uploaded server code in v1.
**How to avoid:** v1 subjects = fake variants and in-process generator output only; stdio launch of real code only inside the container runtime or the human CLI with an explicit flag; document it.

### Pitfall 3: Leak detector false positives
**What goes wrong:** the rule "3 of timestamp/status/error/path anywhere in the output" also fires on ordinary text and structured fields (our own `status`, `error`, a `path` field, plain prose).
**How to avoid:** keep the rule exact for fidelity, report which rule fired, give the fake good variant keys `ok/kind/message/hint`, and put a regression test asserting the good variant never trips it. Do not "improve" the rule silently; changing it changes comparability.

### Pitfall 4: Lenient pass conditions inherited from the runner
**What goes wrong:** `clean_not_found` passes when there is no "Error:" text OR a not-found signal (`no_crash or has_signal`), so a server that returns a wrong non-error answer passes; `empty_search_clean` only checks `no_error`; `auth` check accepts the word "invalid" anywhere.
**How to avoid:** tighten as in the port table; keep the original expect names so source golden files still load, and add a `x-strict` default.

### Pitfall 5: `pass_thresholds` declared, never enforced
**What goes wrong:** `case.yaml` thresholds are parsed by no code; a run is PASS only if every check passes.
**How to avoid:** implement thresholds in `scoring.ts` and test them; document that source "PASS" differs.

### Pitfall 6: Optimistic aggregation and silent tie-breaks
`report.py` `majority` prefers `PASS` on ties (`max` over `(count, name)`). Use FAIL-wins; document.

### Pitfall 7: Leak-guard length mismatch
`golden_fingerprints` keeps strings longer than 8 chars but `check_golden_isolation` only tests fingerprints longer than 16, so short expected answers are never checked and hash entries can never match. Port with one explicit `min_len` (default 8) and test both sides of the boundary.

### Pitfall 8: stdout contamination and banners
Servers (especially Python frameworks) may print banners; stdout must carry only JSON-RPC lines. Non-JSON stdout lines are recorded as `stdout_noise` findings (D1 warning), stderr is only captured and secret-scanned. UNVERIFIED how the pinned FastMCP behaves; part of the pending-human interop run.

### Pitfall 9: Flaky timing tests
Retry/backoff and timeout checks depend on time. Use the mock's request log with timestamps relative to first request and tolerant windows; accept an injectable clock for the fake; mark the real-container variants as human-run.

### Pitfall 10: Unbound checks look like failures of the server
A check with no matching tool is FAIL in the source ("no tool bound = FAIL"). Keep that (it is the study's design) but distinguish `ERROR: ambiguous binding` (our problem) from `FAIL: no tool` in the report.

### Pitfall 11: Non-determinism in the report
Timestamps and durations break golden-file tests. Put them only under `run.generatedAt` and `timings`, and make the rest deterministic so a golden report test is possible (`UPDATE_GOLDEN=1` convention from Phase 14).

### Line-delimited JSON-RPC over streams (spec: stdio transport)
```ts
// Source: modelcontextprotocol.io/specification/2025-11-25/basic/transports (stdio)
export function lineChannel(input: Readable, output: Writable, onMessage: (m: unknown) => void, onNoise: (line: string) => void) {
  let buf = ''
  input.setEncoding('utf8')
  input.on('data', (chunk: string) => {
    buf += chunk
    let i: number
    while ((i = buf.indexOf('\n')) >= 0) {
      const line = buf.slice(0, i).trim(); buf = buf.slice(i + 1)
      if (!line) continue
      try { onMessage(JSON.parse(line)) } catch { onNoise(line.slice(0, 200)) }
    }
  })
  return { send: (m: unknown) => output.write(JSON.stringify(m) + '\n') }
}
```

### Leak detector (port of `looks_like_leaked_error`)
```ts
const LEAK_CORE = ['Traceback (most recent call last)', 'httpx.', 'all shards failed',
  'requests.exceptions', 'ConnectionError', 'JSONDecodeError']
const ENVELOPE_WORDS = ['timestamp', 'status', 'error', 'path']
export function leakReason(text: string, extra: string[] = []): string | null {
  const hit = [...LEAK_CORE, ...extra].find((s) => text.includes(s))
  if (hit) return `substring:${hit}`
  const lower = text.toLowerCase()
  const n = ENVELOPE_WORDS.filter((w) => lower.includes(w)).length
  return n >= 3 ? `envelope:${n}of4` : null
}
```

## Safety Architecture (SC-3)

- Subjects can reach only the mock (loopback). Case env mapping supplies base-URL vars pointing at the mock port and a per-run random canary key; nothing else from the host environment.
- No real host names appear anywhere; criteria test enforces. No `.env` access; the CLI refuses `.env*` arguments like Phase 14's.

Accessibility: follow the Phase 10 conventions (axe tests like `GenerateMcpPanel.a11y.test.ts` for idle, running, done, error states).

**API shape (reuses Phase 8 job pattern; new module, existing code untouched):**
- `POST /api/mcp-test/runs` JSON `{ subject: "fake:good" | "generator:<sample>", cases?: string[], reruns?: 1-3 }` (strict allowlist; reject anything else) -> `202 { id, status: "queued" }`; the run is fire-and-forget (do not await), as in `tryitout/jobs/+server.ts`.
- `GET /api/mcp-test/runs/:id` -> `{ status, progress: { done, total, current }, events, error }` (id validated with the same UUID regex as `isValidJobId` before any lookup; literal response, never spread the record).
- `GET /api/mcp-test/runs/:id/report` -> `report.json` when done (cap size).
- Guards: flag check first (404), one active run at a time globally and per `sessionKey`, `admitSession`/`clientLimit` style cap for anonymous clients, hard caps on cases and reruns, in-memory store with TTL eviction (the Try It Out store never evicts, which was an accepted demo tradeoff; do better here), no persistence of reports unless the CLI `--out` is used, and the same "no auth logic of its own" caveat as Phase 14 (confirm the global hook; open question 8).
- CLI: `npm run mcp-test -- --subject fake:good --case T2-STK-API --reruns 3 --out report.json`; real subjects need `--allow-local-exec` (human-only).

## Risks

1. **Interop is unproven until a human runs real FastMCP.** The client is validated only against our fake and the spec text. Mitigation: strict-by-default framing tests, tolerant handling of noise, pending-human item 2/5.
2. **Hand-rolled client drift** versus spec revisions (spec already at 2025-11-25). Mitigation: known-versions list, report records negotiated version, interop run.
3. **Scoring is only as honest as the mock.** If the mock natively exposes the discriminator capability or is lenient, converters score full marks (exactly what happened with T2-STK-API 9/9). Mitigation: strict mock (reject unknown params), checks 3-10 added to T2, discrimination tests.
4. **Fake variants may be mistaken for evidence about real generators.** Report and UI label fake runs prominently; calibration claims are about the scorer only.
5. **Generated-server runs are inherently runtime-gated.** The headline value (scoring Phase 14 output end to end) is unobservable in CI; only generator-side checks and the fake run unattended.
6. **Security surface:** unauthenticated run endpoint can burn CPU (mock servers, subprocess); caps, single-flight, TTL, flag default off. Uploading third-party servers deferred.
7. **Source quirks lost on purpose** (lenient `clean_not_found`, optimistic ties, unread thresholds) make new numbers incomparable to historic `results.csv` for those items; keep the legacy CSV export and note the deviations.
8. **Phase 14 limitations propagate:** SQL/dataset planners emit only `describe_*` and `query_*` (D-162), so lookup-style checks must bind to `query_*`; the dataset backend emits the first entity only; no composite or HTTP-transport output.
9. **Scope size:** 12 cases x mock behaviours is large; plan waves so T1 + T2 + Tier 4 core + scorer discrimination land first, and mark others as `implemented-minimal` honestly in the fidelity table.
