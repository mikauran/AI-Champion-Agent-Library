## Route decision (Ville: choose proxy or sidecar on the internal network, whichever changes the network guard less)
Recommended default for this run: an app-side MCP proxy route (like the existing LLM proxy `/api/llm/...`: per-lease token, per-job request budget, allow-listed tool names, size caps, no key in the container; the Pi container still reaches only the app on the internal network, so the network guard is unchanged) that acts as MCP client to the LVI-INFO server. How the proxy reaches the server: local-only, the server runs on the host (stdio subprocess started by the app on the host in dev, or HTTP transport on 127.0.0.1 with the app image/host reaching it via the existing host gateway); the Containerfile/app image must not gain python for the release. The sidecar alternative changes the compose topology (a service needing egress while the Pi container stays internal) and so touches the guard more. Planner: verify both against the code (network guard module and compose), write the comparison, record the decision (D-nnn) with revert steps.
How Pi calls it: Pi has no built-in MCP client; options are a staged Pi extension/custom tool for this agent (preferred; check Pi docs via the package's docs/extensions.md after `npm view`/reading the installed package in the pi-runner image or npm cache; do not run containers except via the live-run procedure) or enabling `bash` + curl/node fetch for this agent only (weaker: widens the container surface). Per-agent tool lists may need a small runner change: keep it minimal, flag-gated and tested with the fake runtime.
